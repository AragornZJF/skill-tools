# 进化循环详细规程

论文的每轮迭代分四步：真实任务执行（Inference）→ 提炼（Wiki Maintainer）→ 提案（Skill Proposer）→ 门控（Gating）。本地环境中"训练集 rollout"就是用户的真实任务，因此本规程覆盖后三步，外加对第一步的纪律要求。

开始前确认知识库存在（不存在先跑 `scripts/init_wiki.py`），并读一遍 `wiki/INDEX.md` 了解全局。

## 第零步：真实任务执行（Inference）

- 用户照常执行业务任务，可使用任何现有技能。
- 唯一纪律：**任务执行期间不读 `.wiki-skill/wiki/`**（不变量 5）。
- 任务结束后主动建议：「要把这次执行记录到经验库吗？」——记录方法见 references/raw-capture.md。

## 第一步：提炼（Wiki Maintainer 角色）

目标：把 raw/ 里的零散轨迹编译成结构化知识。输入是轨迹，输出是 Pattern 页和日志更新。

1. **确定本轮输入。** 读 `wiki/INDEX.md` 配置区的「已提炼水位线」，列出 raw/ 中尚未提炼的轨迹文件；INDEX 未记录水位线时（首次运行）全部视为新输入。
2. **逐条根因分析。** 对每条轨迹回答：
   - 结果是成功还是失败？表面症状是什么？
   - 连问几个为什么，找到**可操作的根因**。"上下文不够"不是根因；"改 XX 前没有先读 YY 文件，导致用了已废弃的接口"才是。
   - 这次成败是偶然的，还是会重复出现的模式？
3. **查重。** 对照 INDEX.md 模式表：已有 Pattern 覆盖 → 更新该 Pattern（追加证据、修正根因或修复方案），不要新建；确属新模式 → 按 `assets/templates/pattern-template.md` 新建 `P-<下一个编号>-<slug>.md`。
4. **更新 Wiki。**
   - INDEX.md：新增/更新模式行，更新「下一个模式编号」，把「已提炼水位线」推进到本轮最后一条已分析轨迹。
   - logs.md：按格式追加本轮条目（日期、分析了几条轨迹、新增/更新了哪些模式、一句话结论）。
5. **汇报并建议下一步。** 列出本轮新增/更新的模式，指出其中"已有可操作修复方案、但技能尚未覆盖"的——这些是提案环节的最佳输入。

注意：提炼阶段**不改任何技能文件**。知识先行，动技能是提案环节的事。

## 第二步：提案（Skill Proposer 角色）

目标：从知识生成一次技能创建或补丁，写入 staging/ 待门控。按需阅读，不要一次读完全部文件：

1. **读索引。** 读 `wiki/INDEX.md` 模式表，圈出候选模式。优先选：反复出现（出现次数 ≥2）、有可操作修复方案、尚无技能覆盖或现有技能未解决的。
2. **查台账。** 对每个候选读 `wiki/skill-impact.md`：目标技能以前改过吗？哪次被拒？拒绝原因是什么？被拒过的改法必须有本质不同才可再提。
3. **读模式与证据。** 读候选 Pattern 全文；需要确认细节时按需读它引用的 raw/ 轨迹（只读相关段落）。
4. **形成提案。** 二选一：
   - **新建技能**：在 `staging/<技能名>/` 写 SKILL.md（只写可执行步骤，不搬运知识推理）+ PURPOSE.md（关联 Pattern ID + 设计意图）。
   - **补丁**：把目标技能当前版本复制到 `staging/<技能名>/`，在其中实施修改；整理一份 diff（旧版 vs 新版）；同步更新 PURPOSE.md 的演化记录。
   - 需要门控的技能若没有 tests.md，一并用 `assets/templates/tests-template.md` 建好初稿。
5. **登记。** 在 skill-impact.md 追加提案条目（状态：待门控），logs.md 记一笔。
6. **汇报。** 给用户看：解决哪个 Pattern、改动要点、diff 摘要，请求进入门控。

## 第三步：门控（Gating）

目标：验证候选技能确实更好。通过则合并，不通过则回滚技能——但 Wiki 永不回滚。

1. **确认测试集。** 读该技能的 tests.md；没有就现场创建（用模板），2–5 条真实测试提示 + 期望行为，和用户确认后再继续。
2. **跑基线。** 用当前生效版本执行测试提示，结果记入 tests.md 执行记录表；已有近期基线记录可复用。
3. **跑候选。** 按 `staging/<技能名>/` 版本执行同样提示，记录结果。
4. **对比与确认。** 汇报两版在每条提示上的差异。**用户是最终门控**：明确询问是否合并。
5. **落地。**
   - **通过** → 旧版先备份到 `archive/<技能名>/<日期>-<序号>/`，再把 staging 版本合并到 Skills 层；skill-impact.md 该提案标记「已接受」。
   - **不通过** → 删除 staging 候选，Skills 层保持不动（自然回滚）；skill-impact.md 标记「已拒绝」并**写清拒绝原因**——这是下一轮提案的避坑依据。
6. **收尾。** 无论结果，logs.md 追加门控结论；Wiki 的模式原样保留（不变量 2）。拒绝只说明"这种改法不行"，不说明"这个知识没用"。

## 完整一轮：进化

用户说「进化一轮」时按 提炼 → 提案 → 门控 顺序执行。每步结束简要汇报再进入下一步；门控必须拿到用户确认才能合并。若某步没有可处理内容，如实说明并停在原地。
