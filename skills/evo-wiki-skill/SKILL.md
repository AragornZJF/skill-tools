# evo-wiki-skill：让技能从经验中生长

本 skill 是一个**元技能**：不直接解决业务任务，而是运行一套进化循环，让用户的其他 skill 基于真实使用经验持续变强。核心思想来自 Google WikiSkill 论文——把**经验**（原始轨迹）、**知识**（模式库）、**技能**（可执行 SKILL.md）分成三层，经验先沉淀为知识，知识再指导技能更新。技能更新被拒绝时知识仍然保留，所以每一轮迭代都不会白做。

## 三层架构

| 层 | 位置 | 存什么 | 铁律 |
|---|---|---|---|
| Raw 层 | `<项目根>/.wiki-skill/raw/` | 每次任务的执行轨迹 | 只追加，永不修改或删除 |
| Wiki 层 | `<项目根>/.wiki-skill/wiki/` | 结构化知识：INDEX.md、patterns/、logs.md、skill-impact.md | **永不回滚** |
| Skills 层 | `.agents/skills/<name>/` | 当前生效的技能 | 门控通过才合并，否则回滚 |

技能改动先写入 `<项目根>/.wiki-skill/staging/<技能名>/` 参与门控，通过后才合并进 Skills 层；被替换的旧版备份到 `.wiki-skill/archive/`。

## 五条不变量

执行任何操作前先确认这五条，它们是整个架构有效的前提：

1. **Raw 只追加。** 后续所有分析都靠回溯原始轨迹；覆盖或"顺手清理"原始记录，进化就失去了事实基础。记录有误不删原文，追加一条修正。
2. **Wiki 永不回滚。** 技能被门控拒绝时只回滚技能本身，Wiki 里的模式和"上次为什么被拒"完整保留。下一轮提案必须先读 skill-impact.md，避免重复踩坑。
3. **知识与技能分离。** Wiki 回答"我们知道什么"（症状、根因、证据），SKILL.md 回答"怎么做"（可执行步骤）。不要把大段推理上下文塞进技能——技能从知识里生长，但两者各管各的。
4. **改动必溯源。** 每次技能新建或补丁，都必须能通过 PURPOSE.md 追溯到具体 Pattern ID。说不出"这个改动解决哪个模式"，就不要提交提案。
5. **执行真实任务时不查 Wiki。** 任务执行期间翻看模式库，轨迹就变成"照着答案做"，失去参考价值。Wiki 只在任务结束后的复盘与进化阶段使用。

## 首次使用

若 `<项目根>/.wiki-skill/` 不存在，先初始化知识库骨架（脚本可重复执行，不会覆盖已有文件）：

```bash
python .agents/skills/evo-wiki-skill/scripts/init_wiki.py                # 默认当前目录为项目根
python .agents/skills/evo-wiki-skill/scripts/init_wiki.py --project <路径>  # 或指定项目根
```

（Windows 上若 `python` 无效，改用 `py`。）

（若本 skill 安装在其他位置，把路径换成 skill 根目录下的 `scripts/init_wiki.py`。）

## 子命令路由

按用户意图路由到对应流程；用户用自然语言表达即可，不要求记住命令名：

| 用户意图（示例说法） | 子命令 | 一句话说明 | 详细规程 |
|---|---|---|---|
| "记录一下这次任务"、"存个档" | **记录** | 把执行轨迹写入 raw/ | references/raw-capture.md |
| "复盘一下"、"沉淀经验"、"分析为什么失败" | **提炼** | 根因分析轨迹，更新 Wiki | references/evolve-loop.md「提炼」 |
| "根据经验改进 xx 技能"、"为 xx 写个技能" | **提案** | 从知识生成技能新建或补丁，写入 staging/ | references/evolve-loop.md「提案」 |
| "验证这个改动"、"这版技能行不行" | **门控** | 测试提示对比 + 用户确认，合并或回滚 | references/evolve-loop.md「门控」 |
| "进化一轮"、"跑一遍完整流程" | **进化** | 提炼 → 提案 → 门控 一整轮 | references/evolve-loop.md |
| "看看知识库现状"、"有什么模式" | **状态** | 汇报知识库现状并建议下一步 | 见下 |

**状态**子命令直接执行：统计 raw/ 中未提炼轨迹数（对照 INDEX.md 水位线）、各状态模式数、待门控提案与近期接受/拒绝，最后给出"建议下一步"（例如：有 3 条未提炼轨迹，建议先做提炼）。

## 执行纪律

- **先读再写。** 提炼前先读 INDEX.md 和已有 Pattern（避免重复建模式）；提案前先读 skill-impact.md（避免重复踩坑）。
- **一轮只解决一件事。** 单轮进化聚焦 1–3 个模式，宁深勿泛；其余记入 INDEX 留给下轮。
- **每步结束都汇报。** 说明本步产出了什么、下一步建议做什么；门控必须拿到用户确认才能合并。用户说"进化一轮"时按 提炼→提案→门控 顺序执行，但每步之间仍要简要汇报。
- **没有可处理的内容就如实停下。** 没有未提炼轨迹、没有够格的候选模式时，说明情况，不要硬凑。
- 文件格式规范见 references/wiki-formats.md，全部模板在 assets/templates/。

## 设计出处

架构与循环规则提炼自 Google Research《WikiSkill》论文：三层知识架构（Raw / Wiki / Skills）、四步进化循环（Inference → Wiki Maintainer → Skill Proposer → Gating）、"Wiki 永不回滚"与"知识/技能分离"两个关键设计。论文消融实验显示去掉 Wiki 层平均分回落约 15 个百分点——这正是本 skill 坚持先沉淀知识、再改技能的原因。
