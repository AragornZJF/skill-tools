# Skills 设计模式（Design Patterns）

> 四大模式 + 软件工程智慧迁移。生成技能时按需阅读，决定目录结构与指令写法。

## 〇、四层架构总览

```
                 ┌─────────────┐
                 │  主控层 SKILL.md │  ← 唯一必加载：意图识别及流程路由
                 └──────┬──────┘
         ┌──────────────┼──────────────┐
         ▼              ▼              ▼
     知识层           规范层          执行层
    reference/      templates/      scripts/
    按需加载         套模板输出       确定性计算
    (低频知识)      (格式约束)       (消除幻觉)
```

- **主控层是唯一必加载**——必须薄：只放意图识别及流程路由，不含领域细节。
- 其余三层**按需加载**：知识层按路由表加载、规范层在产出阶段套用、执行层在需要精确计算时调用。
- 加载成本从主控层向外递减，领域深度从主控层向外递增——**越往下越重、越不常用、越要确定性**。

## 一、四大设计模式

### 1. 模板驱动模式（规范层）
- 适用：周报、事故报告、审查报告等**需要标准化输出**的场景。
- 价值：输出严格遵循模板结构 → 可预期、可对比、支持自动化后处理。
- 落点：`templates/` 目录。

### 2. 脚本增强模式（执行层）
- 适用：财务计算、正则匹配、数据转换等**确定性计算**。
- 价值：比大模型推理更精准、更省 Token、更具可复现性。
- **经验法则**：如果在 SKILL.md 中编写公式让 Claude 运行计算——立即停止，该逻辑应移至脚本。
- 落点：`scripts/` 目录。

### 3. 知识分层模式（知识层）
- 遵循 80/20 法则：80% 请求仅需 20% 核心内容。
- 高频知识 → 内联 SKILL.md（零额外读取成本）；低频知识 → `reference/` 按需加载。
- 本质：渐进式披露——不需要的公式不占 Token。

#### 内容归属判断公式
```
内容归属 = 路由必要性 × 使用频率
```

| 路由必要性 \ 使用频率 | 高 | 低 |
|---|---|---|
| **高（参与路由决策）** | ✅ 内联 SKILL.md（如 Quick Reference 表、流程） | ⚠️ 极少用但路由必需 → 内联一句话指针 |
| **低（纯领域细节）** | 🔼 高频但不路由 → 核心条目上提内联，细节留 reference | ✅ 下沉 reference/（公式、基准、陷阱） |

#### 分层自检三连（lint 规则）
1. SKILL.md 里出现公式让 Claude 算？→ 移到脚本（脚本增强模式）。
2. 模板能约束的格式写进了指令？→ 移到模板（模板驱动模式）。
3. 高频知识躺在 reference、低频细节躺在 SKILL.md？→ 按上表对调（知识分层模式）。

### 4. 工具隔离模式（安全层）
- 通过 `allowed-tools` 明确"**禁止做什么**"，比定义"能做什么"更关键。
- 对应权限最小化（Least Privilege）原则。
- 生成技能时以**注释形式**给出 allowed-tools 建议（保持 frontmatter 兼容性）：
  ```yaml
  # 建议 allowed-tools（按需裁剪）：
  # - Read, Grep, Glob, Write, Edit, Bash
  ```

## 二、模式选择决策流

| 判断问题 | 是 → | 否 → |
|---|---|---|
| 需要标准化输出格式？ | 📁 `templates/`（模板驱动） | 无需模板 |
| 有确定性计算/匹配？ | 📜 `scripts/`（脚本增强） | 无需脚本 |
| 知识量 > 500 行？ | 📚 拆分至 `reference/`（知识分层） | 内联知识即可 |
| 需要安全边界控制？ | 🔒 配置 `allowed-tools`（工具隔离） | 使用默认权限 |

- 四个判断**相互独立、不互斥**：可多项全中，也可全部为否（此时纯 SKILL.md，退化为提示模板）。
- 500 行只是经验阈值；真正判据是归属公式——行数是它的粗糙代理。
- 建议顺序：先问"知识量"（决定要不要拆目录），再问"模板/脚本"（决定目录里放什么），最后问"安全"。

## 三、软件工程智慧 → Skills 迁移

| 软件工程经典智慧 | 在 Skills 中的对应 |
|---|---|
| README / 文档 | SKILL.md 主体指令 |
| 配置文件 | frontmatter（name / allowed-tools / model） |
| 分模块目录结构 | scripts/、reference/、templates/ 按关注点分离 |
| 单一职责原则（SRP） | 一个 Skill 只管一件事 |
| 关注点分离（SoC） | 主控/知识/规范/执行各司其职 |
| 懒加载 / 按需引入 | 渐进式披露——reference 按路由表加载 |
| 脚本封装 vs 人脑计算 | 浮点数交给 Python，不让 AI 心算 |
| 模板约束输出 | templates/ 保证格式一致可对比 |
| 权限最小化 | allowed-tools 只给干活需要的工具 |
| 语义化命名 / 意图驱动 | 不写「执行步骤1-2-3」，写「你是一个财务分析师」 |

## 四、一句话

**一个成熟的 Skill = 模板约束输出（可预期）× 脚本接管计算（可复现）× 知识按频分层（省 Token）× 工具最小授权（防越权）。**
